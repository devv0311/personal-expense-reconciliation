# Personal expense reconciliation — capability audit

Audit date: 7 September 2026. Repository: `personal-expense-reconciliation`, local HEAD `a93c9b7` (“Refine the ledger workspace and isolate review decisions”). The checkout was clean when inspection began. This is newer than the referenced status update’s `52c1bd4`. No remote HEAD, deployment or GitHub CI status is asserted here.

**Verdict: the financial engine and several substantial review/reporting screens are implemented, but the website is not a complete end-to-end expense-reconciliation application.** Completing phases 1–21 means completing their narrowed implementation scopes. It does not mean every product requirement, original AI operation or authoring workflow is available in the website.

The most significant missing website workflows are onboarding/master data; statement import; initial normalization/classification; credit/cash-flow classification; receipt/evidence ingestion and correction; manual/external-payer expense creation; multi-payment/multi-expense funding links; initial beneficiary allocation; manual settlements; refund-to-credit linkage; and first Splitwise sync/setup. Some are API-only, some service-only, and some only modeled. Real AI and Splitwise adapters are unconfigured. Rules/learning, analytics, natural language, occasions, message sending and stale Splitwise repair remain unbuilt.

The cash waterfall, item-refund engine/splitter, evidence-match decisions, pair balances, audit findings and redacted proof-pack copy flow are actual code and rendered UI. They should not be dismissed as documentation-only. They work over data that must often be prepared outside the website.

The available conversation was bounded; the audit covers capabilities documented in this checkout and the supplied conversation, not unprovided conversations or files.

- **Implemented** means an actual code path exists; it does not imply a real external adapter is connected.
- **Partial** separates supported calculations/reads from missing authoring, lifecycle or integration paths.
- **Schema/domain only** means a representation exists without a complete application workflow.
- **Absent** means no implementation/registered endpoint/mounted control was found at that layer.
- **P1**: needed to complete ordinary website workflows or prevent materially incomplete financial interpretation; fix before treating the website as operational for personal data.
- **P2**: meaningful product completeness/usability or later capability.
- **P3**: deferred enhancement/architecture work. **—**: no additional gap priority for that row’s accepted scope.

Priorities are audit recommendations, not existing roadmap commitments. Intentional boundaries are labeled separately from missing features. File links target this exact local checkout; line numbers may move after edits.

## Concrete website failures and dead ends

1. **Approve an expense → no way to allocate it.** Review can approve a proposal. Expense detail then says “Nobody has been named a beneficiary yet,” but has no initial allocation form. Its refund distribution controls are not a replacement for beneficiary authoring.
2. **Record a refund → no bank-credit link.** The backend route accepts `adjustmentPaymentId`; the browser request type and form omit it. Users can reduce an expense without connecting that fact to the incoming bank movement. Cash-category approval is also unavailable in the website.
3. **Inspect a receipt → extracted details never appear in full.** `ReceiptFacts` and `useReceipt` are declarations with no callers. The unmatched-evidence inspector exposes a receipt total, but there is no mounted full receipt item/tax/discrepancy review, confirm or correct flow.
4. **Search an older expense → possibly invisible.** `listExpenses` defaults to 200 newest records; the page neither increases that limit nor paginates. Search is client-side over that subset. A result count does not establish the total ledger size.
5. **Investigate an unexplained cash term → generic navigation only.** Waterfall credits/debits are not links to their contributing payments. “Payments with no explanation” goes to the generic Review page, without account/period filtering. Review is not an exhaustive list of unexplained bank movements.
6. **Repair a rejected classification or missing refund ownership → no UI action.** Reclassification, modified proposals and allocation editing have backend paths but no website editors. Existing item breakdowns additionally lack a correction path at the service/API layer.
7. **Explain a net pair balance → settlement detail missing from that screen.** The balance page lists gross obligation contributions, but no repayment lines. In the live seed, contributions of ₹1,600 and ₹900 sit below a ₹900 net balance; the proof pack, not this screen, contains the settlement explanation. Expense-level pending refunds also do not become balance-level warnings.
8. **Reconcile without a connected Splitwise integration → potentially misleading wording.** Code inspection shows `detectSplitwiseDrift` returns empty discrepancies plus a null snapshot when nothing was connected; `DiscrepancyList` unconditionally renders “No discrepancies — the ledger matches” for an empty list. This is a source-verified wording gap; this branch was not exercised against the live seed. It should say that Splitwise was not checked. The separate audit screen correctly displays failed/partial/unsupported read status.

## Recommended completion order

1. Complete the input-to-ledger path: people/account setup, statement import, normalization/classification orchestration, cash-category review and an exhaustive payment workspace.
2. Complete financial authoring: manual/external-payer expenses, funding links, initial allocations/group membership, item entry/correction and manual settlements.
3. Complete evidence/refund reconciliation: upload/note/notification forms, real local extraction preparation and AI transport, receipt confirmation/correction, manual links, refund credit selection and actionable waterfall drill-through.
4. Add operational integrations and protection: authentication, Splitwise authentication/person mapping/first-sync preview, real read adapter and explicit stale repair. Preserve the existing incomplete-read and approval boundaries.
5. Close discoverability/history gaps: ledger pagination/search, transaction/settlement audit detail and visible pending-refund caveats on balances. Then implement rules, analytics, message transport, occasions and natural-language work in the order most useful to daily use.
