## Running it

Requirements: Node.js 20 or later. Install once with `npm install` and `npm --prefix web install`.

- **The owner's real ledger** is started and stopped only by the private launcher in `local-data/`
  (gitignored): `bash local-data/start-real.sh` serves the API on `127.0.0.1:4000` and the website
  on `127.0.0.1:3000`, and records its own process group. `bash local-data/stop-real.sh` stops
  exactly that group.
- **Never** `pkill`/`killall` or kill by a command-line pattern. The synthetic and real stacks run
  identical commands, and a pattern that matched both is what destroyed a ledger on 19 September
  ([process-isolation.md](process-isolation.md)).
- Starting the API applies pending migrations. This release adds **no migration**: the journal has
  22 entries, all of them applied, and `drizzle-kit generate` reports no schema change.
- Synthetic work, such as tests, a QA stack or a scan, uses other ports (4001/3001) and a scratch
  database. See [process-isolation.md](process-isolation.md).

### Stopping, backups and recovery

- **A stop is complete only when the ledger is demonstrably cold.** A free port is not enough. All
  of the following must hold:
  - no `postmaster.pid` in the ledger directory;
  - `global/pg_control` reports the last shutdown completed (`SHUTDOWNED`);
  - no process holds a file open in the directory;
  - none of the stack's processes remain.
- **A backup is a copy of the ledger directory taken only while it is cold.** Keep two:
  - a restore point that is never opened;
  - a verification copy that may be opened read-only to check it.

  Prove both identical to the original by digest.

- **Recovery** is the same in reverse. Stop the stack and prove it cold, move the damaged directory
  aside (never delete it), and copy a restore point into place. PGlite has no `pg_resetwal`, so a
  directory torn by a forced kill cannot be repaired, only restored.

## What was verified, and how far it goes

- **Automated checks:**
  - root typecheck, lint, format, `db:check`, build and the full Vitest suite;
  - `web/` typecheck, lint, format, tests and production build;
  - the integration suite run serially on a real PostgreSQL 18 server (1,319 tests), including the
    racing-correction test.
- **On synthetic data, over HTTP and through the components**, the correction flow:
  - preview with nothing written;
  - commit, giving the expected debt with the amount, payment, funding, category and payer
    unchanged;
  - audit event with its reason;
  - a lost-response retry refused with nothing written;
  - two racing corrections, exactly one of which wins;
  - supersession of an existing split, and the net amount divided after a refund;
  - atomic rollback when the split is refused;
  - every refusal path;
  - the dialog's recovery after a lost answer (done, not recorded, or changed another way).
- **Security, on an isolated synthetic target with authentication on.**
  - An authenticated HawkScan covered 21 described operations: master data, statement preview and
    import, notes, decisions, splits, the correction and its preview, expense reads and history,
    evidence metadata and content, intake (refusal path), and sign-in.
  - Two scans ran, one before and one after the fixes. Both passed the threshold, with one Low
    finding left: `GET /api/session` returns the signed-in owner's own email to that owner. That is
    by design: the navigation shows who is signed in, and without a session the route returns no
    email.
  - 40 scripted probes covered:
    - session lifecycle and cookie flags, forged and signed-out tokens, and password change
      without a session;
    - the origin and `Host` guards with a valid session;
    - multipart abuse: SVG, HTML, mismatched bytes, traversal filenames, an oversized file,
      malformed bodies;
    - evidence content reads;
    - the intake token, including a one-character difference;
    - the correction route's authorization.

    They found the two defects fixed above, and all 40 pass after the fixes.

  - **Not scanned:**
    - the website itself;
    - routes outside the described subset;
    - the multipart upload, which the scanner sends as JSON;
    - password change, excluded so the scanner cannot lock itself out. It was probed by hand.

  This is bounded evidence, not clearance.

- **On the owner's real ledger, read-only:**
  - The current build was first rehearsed on a disposable copy of the ledger. It started, served
    13/13 API views and rendered 8 routes plus the correction screen at 1280 px and 375 px, with no
    alert and no horizontal overflow. Afterwards the copy's 43 tables were unchanged.
  - Then the original ran, through the private launcher. It served 13/13 GET views, and the browser
    sweep repeated the same 8 routes plus the correction screen at both widths, with no console
    error on the real site. The correction was offered on exactly the expenses approved as personal
    and on no others.
  - It was stopped cold. Before and after: 43/43 tables identical by row count and digest,
    migrations 22 → 22, and only the shutdown WAL segment and `pg_control` differ. No import,
    approval, correction, repair, reclassification or duplicate decision was made.
- **Dependencies:**
  - `npm audit --omit=dev` reports 0 in both packages, and the root development audit reports 0.
  - `web/` keeps one development-only chain (`eslint-config-next` → `@next/eslint-plugin-next` →
    `fast-glob` → `micromatch` → `braces` ≤ 3.0.3, GHSA-vfj7-8cjw-p6xm). No patched `braces`
    release exists, and npm's offered fix is a downgrade to `eslint-config-next` 14.
  - It is unreachable here. The plugin calls `fast-glob` only for a `settings.next.rootDir` pattern,
    and this configuration sets none, so no glob runs and no attacker-supplied pattern exists.
    **Known limitation**, to re-check when `eslint-config-next` updates.

## Not built, deliberately

- **Correcting a kind in the other direction** (shared → personal) **or between two shared
  kinds.** That would unwind debts that may already be settled or synced, and it needs its own
  design (compare ADR-0055). Changing who shares a shared expense already works: save a new split.
- **A sign-in attempt limit.** On the default loopback bind only local processes reach the API, and
  scrypt makes each guess slow. Add one before binding to a network interface
  ([security-model.md](../security/security-model.md)).
- **Live providers** (Splitwise, bank and balance adapters, a model, message transport, forwarding)
  are connected nowhere, and each refuses by name until configured. Connecting one is a
  deliberate, separate act.
